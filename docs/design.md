# EventPulse — Design and Build Checklist

As of 2026-10-22. Deadline: finished, documented repository by Nov 8, with Nov 9 as buffer.

## Scope

EventPulse is a small event-processing backend that proves one thing: you can run Kafka consumers in C# that survive crashes, duplicates and dependency failures without losing or double-applying business events.

The domain is a fictional e-commerce order flow. Three event types are enough: `OrderPlaced`, `PaymentCompleted`, `OrderCancelled`. The system accepts them over HTTP, puts them on Kafka, and workers apply them to an order ledger in PostgreSQL. That is the whole product.

What the repo must prove, in order of priority:

1. A consumer can crash mid-batch and the ledger stays correct after restart.
2. The same event delivered twice changes the ledger once.
3. Events for one order are applied in order; events for different orders run in parallel.
4. A poison event, one that cannot be read as a valid event, is dead-lettered immediately with no retries and does not block the partition. A business conflict is also dead-lettered without retries.
5. The API refuses excess traffic using a Redis rate limit, and behaves predictably when Redis is down.
6. Every claim above has a test or a written failure-injection result behind it.

Deliberately out, do not build even if there is time:

- A frontend or dashboard of any kind
- Authentication, users, tenants
- Kubernetes, cloud deployment, Helm
- More than one worker project (one `Worker` with several consumers inside it)
- OpenTelemetry, Grafana, Prometheus (a `/health` endpoint and structured logs are enough)
- A transactional outbox **unless** milestones 1–3 are done by Nov 1

Stretch, only after the definition of done is met: outbox, a k6 load test with numbers in the README.

## Architecture

Two deployable .NET 8 projects plus three infrastructure containers, all started with one `docker compose up`.

| Component | Project | Responsibility |
| --- | --- | --- |
| API | `EventPulse.Api` (ASP.NET Core minimal API) | Validate incoming events, rate-limit by client key via Redis, publish to Kafka, return 202 |
| Worker | `EventPulse.Worker` (.NET Worker Service) | One `BackgroundService` per consumer group; apply events to Postgres; retry and dead-letter |
| Shared | `EventPulse.Contracts` (class library) | Event envelope, event payloads, topic names, serialization |
| Kafka | `confluentinc/cp-kafka` single broker, KRaft mode | Durable log; `orders.events` (6 partitions), `orders.events.dlq` |
| PostgreSQL | `postgres:16` | `orders` ledger, `processed_events` idempotency table, `dead_letters` |
| Redis | `redis:7` | Fixed-window rate limit per API key; nothing else |

```
Client ──POST /events──▶ EventPulse.Api ──publish──▶ Kafka (orders.events, key=orderId) ──dead-letter──▶ orders.events.dlq
                              │                           │
                         INCR + TTL                    consume
                              ▼                           ▼
                            Redis                  EventPulse.Worker ──apply──▶ Postgres (ledger)
                    (rate-limit counters)        (group order-ledger:
                                                  apply, retry, dead-letter)
```

The API never touches Postgres. The Worker serves only `/health` and `/metrics` on port 8081, not published to the host, for compose health checks. That split is what makes the crash tests meaningful: killing the Worker cannot affect ingestion, and the only shared state is the Kafka log. The Worker can be stopped for an hour and the API keeps accepting events.

Within the Worker, the first version runs one consumer group (`order-ledger`) that applies all three event types. A second group (`order-notifications`, writes a row to a `notifications` table) is added in milestone 2 only to demonstrate that two groups read the same log independently; it is otherwise trivial.

## Event model

Every message on Kafka is one envelope. The `eventId` is generated by the client (or by the API if missing) and is what makes idempotency possible; the `orderId` is the partition key.

```json
{
  "eventId": "7c1f0b2e-4a0d-4d2f-9a3b-6f8b2a1c9e10",
  "eventType": "OrderPlaced",
  "orderId": "ord_10492",
  "occurredAt": "2026-10-25T14:03:11Z",
  "schemaVersion": 1,
  "payload": { "customerId": "cus_77", "amountMinor": 24900, "currency": "DKK" }
}
```

| Event type | Payload fields | Ledger effect |
| --- | --- | --- |
| `OrderPlaced` | `customerId`, `amountMinor`, `currency` | Insert order with status `Placed`; an `orderId` that already exists under a different `eventId` is a conflict |
| `PaymentCompleted` | `paymentId`, `amountMinor` | Order status `Placed` → `Paid`; any other current status is a conflict |
| `OrderCancelled` | `reason` | Order status `Placed` → `Cancelled`; from `Paid` it is a conflict |

Rules:

- Serialization is `System.Text.Json`, camelCase, unknown fields ignored. No Avro, no schema registry.
- Kafka message key = `orderId` as UTF-8. Headers carry `eventType` and `schemaVersion` so a consumer can route without deserializing the body.
- A conflict (e.g. `PaymentCompleted` for a cancelled order) is a **business failure**, not a transient one. It is recorded in `dead_letters` immediately with no retries.
- An `OrderPlaced` for an `orderId` that already exists, under a different `eventId`, is **dead-lettered as `Conflict`** with detail `DuplicateOrder`. The insert would fail the same way on every attempt, so treating it as transient would block the partition forever.
- An event for an unknown `orderId` (a `PaymentCompleted` arriving before its `OrderPlaced`) is **dead-lettered as `Conflict`** with detail `OrderNotFound`, with no retries. All events for an order are on one partition and consumed in order, so by the time it is read the order's `OrderPlaced` has already been processed or dead-lettered; a retry cannot change that.

## Kafka topics and consumer groups

Two topics, created by a one-shot `kafka-init` container in compose so the broker is never relied on to auto-create them.

| Topic | Partitions | Retention | Purpose |
| --- | --- | --- | --- |
| `orders.events` | 6 | 7 days | All business events, keyed by `orderId` |
| `orders.events.dlq` | 1 | 30 days | Events that failed permanently; original message plus `x-failure-reason`, `x-failure-detail`, `x-attempts`, `x-source-partition`, `x-source-offset` headers |

| Consumer group | Reads | Writes | Why it exists |
| --- | --- | --- | --- |
| `order-ledger` | `orders.events` | `orders`, `processed_events`, `dead_letters`; publishes to DLQ | The real work |
| `order-notifications` | `orders.events` | `notifications` | Proves two groups consume the same log independently; ~30 lines |

Client configuration that matters, in `appsettings.json`, not scattered in code:

- Producer: `Acks=All`, `EnableIdempotence=true`, `MessageSendMaxRetries=3`. The API awaits the delivery report before returning 202; a failed produce returns 503.
- Consumer: `EnableAutoCommit=false`, `AutoOffsetReset=Earliest`, `MaxPollIntervalMs=300000`. Offsets are committed by the handler, never by a timer (see Reliability).
- One `IConsumer` per `BackgroundService`, one `BackgroundService` per group. With 6 partitions you can run up to 6 Worker instances per group; the crash tests run 2.

Run the Worker twice locally (`docker compose up --scale worker=2`) to watch a rebalance in the logs. That is the cheapest demonstration of consumer groups there is.

## PostgreSQL schema

Four tables, EF Core with a single migration per milestone. No repositories, no unit-of-work abstraction; `DbContext` is the unit of work.

```sql
create table orders (
  order_id      text primary key,
  customer_id   text not null,
  amount_minor  bigint not null,
  currency      char(3) not null,
  status        text not null,          -- Placed | Paid | Cancelled
  version       int not null default 1, -- optimistic concurrency
  updated_at    timestamptz not null
);

create table processed_events (
  event_id       uuid primary key,
  consumer_group text not null,
  processed_at   timestamptz not null
);

create table dead_letters (
  id               bigserial primary key,
  event_id         uuid,                   -- null when it could not be read from the message
  event_type       text,                   -- null when it could not be read from the message
  order_id         text,
  reason           text not null,          -- Conflict | Malformed | RetriesExhausted
  detail           text not null,          -- specific cause, e.g. OrderNotFound, InvalidTransition, DuplicateOrder, InvalidEnvelope
  attempts         int not null,
  raw_message      jsonb not null,         -- a body that is not JSON is stored as a JSON string of its text
  failed_at        timestamptz not null,
  dlq_published_at timestamptz             -- set once the DLQ publish is acknowledged
);

create table notifications (
  id            bigserial primary key,
  event_id      uuid not null unique,
  order_id      text not null,
  message       text not null,
  created_at    timestamptz not null
);
```

The one that matters is `processed_events`. The handler inserts the `eventId` in the **same transaction** as the ledger change. A duplicate delivery hits the primary key, the transaction rolls back, and the handler treats the unique violation as "already done" and commits the offset. That is the whole idempotency mechanism; there is no need for anything cleverer.

## Reliability design

The consumer loop is the heart of the project. Every decision below is one an interviewer can ask about, so each has a one-line reason.

**Processing loop, per message**

1. `Consume()` one message.
2. Deserialize the envelope. Failure → `dead_letters` with reason `Malformed`, publish to DLQ, commit offset. No retry: the bytes will not change.
3. Open a Postgres transaction. Insert into `processed_events`. Unique violation → rollback, log `duplicate`, commit offset, next message.
4. Apply the ledger change. Conflict → rollback, write `dead_letters` with reason `Conflict` in a fresh transaction, publish to DLQ, commit offset.
5. Transient error (Postgres unreachable, timeout) → rollback, wait, retry **the same message in place**. That is one attempt plus five retries, 6 attempts in all, with waits of 0.5 s, 1 s, 2 s, 4 s and 8 s between them (`baseDelay * 2^(retry - 1)`, `baseDelay` = 0.5 s). The consumer does not advance and the offset stays uncommitted. Each attempt is bounded by a 2 s connection timeout and a 2 s command timeout, set in the shared connection string, so an unreachable or paused Postgres fails an attempt in about 2 s instead of hanging on Npgsql's defaults (15 s and 30 s). The timeouts apply to both consumers.
6. Retries exhausted → `dead_letters` with reason `RetriesExhausted`, as detail the type and message of the innermost Npgsql exception followed by those of its root cause (`Npgsql.NpgsqlException: Failed to connect to … ---> System.TimeoutException: …`), `attempts` = 6 and `x-attempts: 6`; publish to DLQ, commit offset.
7. Success → commit transaction, then commit offset.

**Why offsets are committed after the database commit, not before**

If the Worker dies between step 7's transaction commit and the offset commit, the message is redelivered on restart. Step 3 catches it as a duplicate. Net effect: at-least-once delivery from Kafka, exactly-once effect on the ledger. The reverse order (offset first) would lose the event on a crash. This is the single most important sentence in the README.

**Why retry in place rather than a retry topic**

A retry topic breaks per-order ordering: a retried `OrderPlaced` can land after the `PaymentCompleted` that followed it. During a full outage, retrying in place blocks the partition for roughly 28 s before dead-lettering, not 15: 15.5 s of waits (0.5 + 1 + 2 + 4 + 8) plus up to 2 s of timeout for each of the 6 attempts. That is acceptable here. Note the trade-off in the README; a retry topic is the right answer when head-of-line blocking costs more than ordering.

**Graceful shutdown**

`StoppingToken` is checked between messages, never mid-transaction. On cancellation: finish the current message, commit its offset, `Close()` the consumer so the group rebalances immediately rather than after `session.timeout.ms`. Test: send SIGTERM mid-batch, confirm zero duplicates and zero gaps.

**Concurrency**

One message at a time per consumer instance. Parallelism comes from partitions and from running more Worker instances, not from `Task.WhenAll` inside a consumer. That keeps the offset-commit reasoning trivially correct. State it explicitly; a reviewer will otherwise assume you missed it.

**Unclassified exceptions**

An exception in the handler that is not classified (bug in your own code) counts as transient and goes through the retry path. After exhaustion it is dead-lettered, so a bug cannot wedge a partition forever.

**When the dead-letter write itself fails**

`dead_letters` lives in Postgres, so the outage that exhausted the retries usually also fails the `RetriesExhausted` write. The write is retried in place every 8 s, bounded by a deadline of 4 minutes counted from when the message was consumed. Past the deadline the Worker logs at Error and stops the host without committing the offset; the message is redelivered on restart, and compose restarts the Worker (`restart: unless-stopped`). Each failed write counts in `dead_letter_write_retries`. The 4-minute bound keeps one message under Kafka's default `max.poll.interval.ms` of 5 minutes, so the consumer is never evicted from the group mid-retry.

**Retries in `order-notifications`**

The notifications consumer uses the same retry schedule through the same shared code, but it has no DLQ. After the schedule it keeps retrying at the 8 s cap under the same 4-minute deadline, then logs at Error and stops the host without committing. It never skips the message.

## Redis

Redis does one job: a fixed-window rate limit on `POST /events` of 100 requests per 10-second window per API key. The key comes from the `X-Api-Key` header; a request without it gets 400. The limit, window and timeout are in the `RateLimit` section of the API's `appsettings.json`. One job done properly beats three done half-way.

**Algorithm: fixed window with atomic increment**

```
key = ratelimit:{apiKey}:{floor(now / 10s)}
n   = INCR key
if n == 1: EXPIRE key 10
if n > 100: return 429, Retry-After = seconds left in the window
```

INCR and EXPIRE run in one Lua script (`EVAL`), so a connection dropped between the two commands cannot leave a key with no TTL. Use `StackExchange.Redis` with one shared `ConnectionMultiplexer` registered as a singleton.

Fixed window is chosen over sliding log because it is two Redis operations and the burst-at-boundary weakness is easy to explain. Say so in the README; being able to name the weakness is the point.

**When Redis is down: fail open**

If the multiplexer is disconnected, the script takes longer than 200 ms, or the call fails with a `RedisException`, the API logs a warning (`ratelimit bypassed, Redis <reason>`), increments a `ratelimit_bypassed` counter, and **accepts** the request without counting it. The multiplexer is created with `AbortOnConnectFail = false`, so the API also starts while Redis is down and reconnects in the background. Reason: the rate limit protects Kafka from abuse, it is not a security boundary, and refusing all traffic because a cache died is the worse failure. This is a decision, not a default; the README says what the fail-closed alternative would protect against and when you would pick it.

**Tests**

- 100 parallel requests from one key within one window: exactly 100 succeed, the 101st gets 429.
- Two keys in parallel do not interfere.
- `docker stop redis` mid-test: requests continue with 202, warning logged, counter increments.
- `docker start redis`: limiting resumes without an API restart (the multiplexer reconnects).

## Delivery guarantees and known failure windows

Write this table into the README on day one as hypotheses. Each row gets a "Verified" date once the matching failure test has run. Rows that stay unverified on Nov 8 are listed as untested, not deleted.

| Scenario | Expected outcome | Why | Verified |
| --- | --- | --- | --- |
| Worker killed after DB commit, before offset commit | Event redelivered, detected as duplicate, ledger unchanged | `processed_events` PK | |
| Worker killed mid-transaction | Transaction rolled back, event redelivered, applied once | Postgres atomicity + redelivery | |
| Same event POSTed twice | Second is accepted by the API (202) but ledger changes once | Idempotency is in the consumer, not the API | 2026-11-01, `duplicate-events.sh` |
| Kafka broker restarted while Worker is consuming | Worker reconnects, resumes from last committed offset, no loss | Committed offsets are durable in Kafka | |
| Postgres down for 10 s | Retries with backoff, succeeds when DB returns, no dead letters | 6 attempts, waits sum to 15.5 s | 2026-11-01, `pause-postgres.sh 10` |
| Postgres down for 60 s | Events dead-lettered as `RetriesExhausted`; partition continues afterwards | Retries bounded by design | 2026-11-01, `stop-postgres-long.sh 60` (PASS), `pause-postgres.sh 60` (REPORT) |
| Postgres down long enough that an `OrderPlaced` is dead-lettered as `RetriesExhausted` | The order's later `PaymentCompleted` or `OrderCancelled` is dead-lettered as `Conflict` / `OrderNotFound` with no retries and its offset is committed. The order has no ledger row; its notifications are still written. Nothing repairs it automatically. | Same partition, one message at a time: the later event is read only after the `OrderPlaced` dead letter is committed, so the order can never exist when it is applied | 2026-11-01, `stop-postgres-long.sh 60` (PASS), `pause-postgres.sh 60` (REPORT) |
| Redis down | API accepts all traffic, warning logged | Fail open by decision | 2026-11-01, `stop-redis.sh 30` |
| Malformed JSON published | Dead-lettered immediately, partition continues | No retry for non-transient | 2026-11-01, `poison.sh` |
| 2 Worker instances, one killed | Partitions rebalance to survivor within session timeout, no loss | Consumer group protocol | |

Any dead-lettered `OrderPlaced` with a readable `orderId` has the same `OrderNotFound` knock-on, whatever the reason it was dead-lettered. Replaying the original messages requires deleting their `processed_events` rows first; otherwise they are skipped as `Duplicate`.

**Known window the design does not close**

The API publishes to Kafka and returns 202. If the produce call succeeds but the API crashes before responding, the client may retry with the same `eventId`, which is harmless, or with a new one, which creates a duplicate business event the system cannot detect. Closing this requires the client to supply `eventId` (recommended in the API docs) or an outbox on the client side. State this plainly; pretending it does not exist is worse than having it.

## Failure-injection test plan

Every experiment is a shell script in `tests/chaos/` that anyone can rerun, plus a short entry in `docs/failure-tests.md` with the command, what was expected, what happened, and the exact log lines. Numbers come from the script's output, never from memory.

The seed is a `scripts/seed.sh` that POSTs 1,000 events for 500 orders with a known final state: every order gets `OrderPlaced` followed by `PaymentCompleted` (even-numbered orders, ending `Paid`) or `OrderCancelled` (odd-numbered orders, ending `Cancelled`). A `scripts/verify.sh` queries Postgres and prints `OK` or which check failed. Every chaos run is: seed in the background, inject the failure, wait for consumer lag to reach 0, verify.

| # | Script | Injection | Pass condition |
| --- | --- | --- | --- |
| 1 | `kill-worker.sh` | Per cycle, a fresh seed; `docker kill worker` 2–13 s into it, `docker start` 5 s later | `verify.sh` prints OK in every cycle; `Duplicate` and open-transaction EOF lines are printed as evidence, not required |
| 2 | `duplicate-events.sh` | Seed, then replay the same 1,000 POSTs | OK; `processed_events` has 1,000 rows, not 2,000 |
| 3 | `restart-kafka.sh` | `docker restart kafka` mid-seed | OK; Worker logs show reconnect and resume |
| 4 | `pause-postgres.sh` | `docker pause postgres` for 10 s mid-seed | OK; logs show retries, zero dead letters |
| 5 | `stop-postgres-long.sh` | `docker stop postgres` for 60 s mid-seed, then `docker start`; a second 20-order seed after the restart | Postgres ready within 60 s; lag 0 on both groups; ≥ 1 `RetriesExhausted` row; every other row is `Conflict` / `OrderNotFound` for an order whose `OrderPlaced` was `RetriesExhausted`; every wrong order has a dead letter and the `processed_events` and notifications checks pass; no `Deadline passed`; the second seed verifies OK with no dead letters |
| 6 | `stop-redis.sh` | `docker stop redis` for 30 s mid-seed, then `docker start`; then bursts of 250 requests under one key until one gets a 429 | Redis answers PING within 60 s; every seed request gets 202; API logs ≥ 1 `ratelimit bypassed`; lag 0 on both groups; OK; no dead letters; a burst starting within 60 s of PONG gets a 429 |
| 7 | `poison.sh` | Publish 5 malformed messages directly with `kafka-console-producer` | 5 rows in `dead_letters` with `Malformed`; seed still completes OK |
| 8 | `rebalance.sh` | `--scale worker=2`, kill one mid-seed | OK; survivor's log shows partitions assigned |
| 9 | `sigterm.sh` | `docker stop worker` (SIGTERM, 10 s grace) mid-seed, restart | OK; zero `duplicate` lines (clean shutdown committed everything) |

Integration tests in `tests/EventPulse.IntegrationTests` use Testcontainers for Kafka, Postgres and Redis and cover the same cases 1, 2, 4 and 7 in-process, so CI exercises them on every push. The chaos scripts are the human-readable version of the same evidence.

## Observability

Enough to debug the chaos tests and nothing more.

- Structured logging with the built-in `ILogger` and JSON console output. Every log line from the consumer carries `eventId`, `orderId`, `partition`, `offset`, `attempt`.
- `GET /health` on the API: returns 200 if the Kafka producer can reach the broker, with a `redis: ok|degraded` field. The Worker exposes the same on an internal port for compose health checks.
- Five counters, exposed as a plain `GET /metrics` JSON object on the Worker: `processed`, `duplicates`, `retries`, `dead_lettered`, `dead_letter_write_retries`. Incremented in memory; reset on restart. That is the dashboard.
- Consumer lag is read with the Kafka CLI (`kafka-consumer-groups --describe --group order-ledger`), not built into the app. Put the command in the README.

OpenTelemetry would take a day to wire and a day to make the traces look right. If the core is done by Nov 5 and nothing else is pending, add it; otherwise it goes in "what I would do next".

**Before the first commit**

- `.gitignore` contains `.mcp.json`, `bin/`, `obj/`, `.env`.
- `.editorconfig` with `dotnet_diagnostic` severities and `csharp_style_*` rules you actually want; run `dotnet format --verify-no-changes` in CI.

**Written by hand, never generated**

- `README.md`. Plain structure: what it is, how to run it, the guarantees table, measured numbers, known limitations, what you would do next. No badges, no feature bullet lists, no adjectives like robust or comprehensive.
- `docs/decisions.md` and `docs/failure-tests.md`. These are your interview notes; writing them is how you learn the material.
- `OrderLedgerConsumer.cs`, the first version. It is the style reference every later file is matched against.
- All commit messages.

**Commit discipline**

- One logical change per commit. Imperative, lower-case, under 60 characters: `add kafka producer to api`, `retry transient failures in place`.
- Commit after every bounded task, after reading the diff.
- `docs/decisions.md` gets one dated entry per design decision, 3–5 lines each. This is the file you re-read before an interview.

2. Chaos scripts 1, 2, 4, 6 and 7 pass and are documented with real output. (3, 5, 8, 9 are strongly wanted but not blocking.)
